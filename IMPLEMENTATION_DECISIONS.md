# Technical decisions (append-only log)
1. Existing `POST /api/v1/recommendations` (stateless) is untouched; authenticated `POST /api/v1/recommendations/runs` + history added. Stateless route is disabled only when NODE_ENV=production AND a database is configured (override: ENABLE_STATELESS_RECOMMENDATIONS) so existing tests that use NODE_ENV=production without a DB keep passing.
2. Domain values (importance, status, ...) are stored as `String` columns with CHECK constraints instead of Prisma enums. DB value = API value = Python value, so there is no enum-name/@map translation layer to get wrong. Validation is in Node validators + DB CHECKs.
3. New feature code lives in `src/modules/<feature>/` (validator, repository, service, controller, routes) because existing static tests forbid `Date`, `.sort(` etc. in `src/{services,validators,mappers,clients,routes}`; those tests are not modified.
4. DB-backed routes mount only when `deps.prisma` is passed to `createApp` (server.js passes it when DATABASE_URL is set). `npm test` therefore stays hermetic; DB tests run via `npm run test:db` (real PostgreSQL, `worktodo_test`).
5. Task dates are `DATE`; session wall-clock is `TIMESTAMP(0)` without time zone, converted only in `utils/dates.js` (UTC-labelled Date), API returns `YYYY-MM-DD HH:mm:ss`. Audit instants are `TIMESTAMPTZ(3)`. `UserPreferences.timeZone` (IANA) is used only for day bucketing.
6. Tasks are soft-deleted (`deletedAt`). History rows keep nullable `taskId` (ON DELETE SET NULL) + `taskNameSnapshot` + `taskSnapshot` JSON; runs keep their own session-context snapshot.
7. `Task.importanceRank` (1-4) is a denormalized sort key maintained by the service so the table can sort by importance in SQL.
8. Auth: Argon2id; 15-min HS256 access JWT (jose) held in memory by the SPA and tied to a DB session (`sid`) so logout/revocation is immediate; rotating refresh token (random 32 bytes, SHA-256 stored) in an HttpOnly SameSite=Strict cookie scoped to `/api/v1/auth`; reuse of a rotated token revokes the whole family; CSRF = SameSite + Origin allowlist + required `X-Requested-With` header; manual CORS allowlist; express-rate-limit on auth endpoints. Cookies are parsed/serialized by a small local helper (no `cookie` dependency).
9. Email: provider abstraction; only `console` (dev: reset link printed to server log) and `none` exist. No delivery is claimed. Email verification flow is out of scope (`isEmailVerified` stays false).
10. Theme: `light` and `dark` both functional through CSS variables (dark palette derived from the approved warm palette). Notification preference is stored only (no delivery exists) and the UI says so.
11. Recommendations: Node loads the user's tasks server-side (never from the client), sends active tasks + newest inactive ones (max 500 total; >500 active -> 422), runs the existing validate/map/ML/validate pipeline, then saves run+items+exclusions in one transaction. Run with zero tasks is rejected (422) instead of saved.
12. Dashboard "Today's Recommendation" reads the latest persisted run (no ML call on load). Insights headline cards are lifetime snapshots; the 7/30/90-day filter drives the time-series charts; "Avg. Focus Time" = average planned available minutes (sessions are plans, not timed work).
13. Frontend: Tailwind 3.4 (postcss), tokens as CSS variables; `build` = `vite build`, `typecheck` = `tsc --noEmit` (separate so a type error never hides a bundling result).


## Refinements made during implementation (consistent with decisions 1-13)
14. **Module layout**: each feature has `*.validator.js` / `*.service.js` / `*.routes.js` (+ mapper). The repository layer is folded into the service (Prisma is called directly) to keep the code small; services take `prisma` by injection, which is how they are unit-tested with an in-memory stand-in.
15. **Access-token `sid` = refresh-token family id**, not the single AuthSession row id, so rotation does not invalidate in-flight access tokens. A session is live while any non-revoked, non-expired row of the family exists.
16. **Refresh race**: presenting a just-rotated refresh token within 10 s returns `401 refresh_race` WITHOUT revoking the family (two tabs refreshing together). Outside the window it is treated as theft and the whole family is revoked. The frontend single-flights refresh and retries once on `refresh_race`.
17. **Recommendation context**: all active tasks (Pending/In Progress) + at most 25 most-recently-updated inactive tasks are sent, so Python reports them as "Task not active" without flooding Excluded Tasks. >500 active tasks -> 422 `too_many_tasks`.
18. **CSRF**: every state-changing request under the database routes requires header `X-Requested-With: WorkToDo` and, when an Origin header is present, an allow-listed Origin. Stateless endpoint unchanged.
19. **Consequence "None"**: the API/DB store `None` only (Python also accepts `No consequence`; the UI offers `None`).
20. **Dashboard "Pending Tasks"** = Pending + In Progress; `completionPercentage` = Completed / all non-deleted tasks (Cancelled counted in the total).
21. **Added pages beyond the nine**: `/forgot-password` and `/reset-password` (required for a working reset flow); 404 page.
22. **JWT**: `jose` HS256 with issuer/audience checks and a DB-backed session check on every request (revocation is immediate).
23. **Focus timer = new `FocusTimer` + `FocusTimerPause` models**; the old `FocusSession` stays a planned-context record. Partial unique indexes: one running/paused timer per user, one open pause per timer.
24. **Elapsed time** = (end or now − startedAt) − Σ pauses, computed on the server (`timer.calc.js`), floored to seconds. Clients cannot send timestamps. The browser only adds the wall-clock delta since the last fetch and resyncs (30 s, on focus/reconnect). Finish/cancel freeze `actualFocusedSeconds` / `totalPausedSeconds`.
25. **Transitions** are status-conditioned `updateMany` (409 `invalid_transition`); a second start → 409 `timer_already_active`; a P2002 from the partial index maps to the same 409. Starting on a Pending task sets it In Progress; `finish` may complete the task.
26. **Insights "Avg Focus Time"** now means actual focused time per finished timer; planned availability is shown separately.
27. **Dependencies**: `TaskDependency` edge table with composite owner FKs. `dependencyStatus` is derived (none → `No dependency`; any Pending/In Progress prerequisite → `Blocked`; else `Ready`), not client-writable; stored column synced in transactions and recomputed at run time. Cycle check = DFS under a user-row `FOR UPDATE` lock; max 20 prerequisites; deleting a task removes its edges and recomputes dependents. Python rules untouched.
28. **Feedback**: `RecommendationFeedback`, unique per (user, item), PUT upsert / DELETE, 4 types, comment ≤500, composite FKs enforce run and item ownership.
29. **Migrations stay additive**: migration 2 only adds tables/indexes. Use `prisma migrate deploy` (partial indexes are invisible to Prisma, so `migrate dev` may show drift).
30. **Lockfiles**: not generated (no network); stale backend lock removed; `npm install` creates them. Declared in docs, not hidden.
31. **Security audit result** (code read, not penetration-tested): no tokens in localStorage (only the theme value is stored); the access token is in memory; refresh is an HttpOnly/SameSite=Strict/path-scoped cookie (Secure in production); only SHA-256 hashes of refresh/reset tokens are stored; logs contain no tokens except the dev-only console email provider, which prints the reset link by design (never in production); every data query is scoped by `userId` and foreign ids give 404.
32. **Complexity**: feeds ML energy suitability (5%). Kept in DB/API/ML; removed from the UI; Node defaults new tasks to `Moderate` (optional in the API for old clients); PATCH never touches it. Model, weights and artifacts unchanged.
33. **Migration 3** (`20261126000000_complexity_default_timezone_default`): only changes two column DEFAULTs (`Task.complexity='Moderate'`, `UserPreferences.timeZone='Asia/Kolkata'`). No row is touched. Verified on PG16 with existing data.
34. **Scheduler** is a pure module (`backend/src/modules/scheduler`): integer-minute wall-clock axis, no time zone/DST maths, no clock or randomness (caller injects `now`), ML ranking is only an order hint with a transparent fallback (due date, importance, name, id). Buffers: preparation+travel before, travel after. Placement is all-or-nothing per task (a split task is either fully placed or reported unscheduled with a reason). Overdue tasks are scheduled ASAP with an `overdue` warning; other tasks that cannot fit before their deadline are reported, never placed late.
35. **Validator** is independent of the engine and is meant for backend enforcement of drag-and-drop and approval; the engine self-checks with it.
36. **Time zone**: default Asia/Kolkata for new users; existing users keep their stored zone; a notice offers the device zone when the stored zone is UTC.
37. **Migration 4** (`20261127000000_planner`) is additive only: new tables `Appointment`, `AppointmentHistory`, `UnavailablePeriod`, `ScheduleVersion`, `ScheduledBlock`, `TaskPostponement`; new nullable/defaulted columns on `UserPreferences` and `Task`. CHECK constraints, composite owner foreign keys and two partial unique indexes (one open draft and one approved version per user). Applied on PostgreSQL 16 over existing rows. Never use `prisma migrate reset`/`dev`; use `migrate deploy`.
38. **Appointments are their own model**, not a task type: they are fixed, have buffers and are never auto-moved. Overlap is rejected (409) under a per-user `FOR UPDATE` lock; edits use an optimistic `revision`; every change writes history.
39. **Drafts, approval, versions**: generation never touches the approved schedule. At most one draft and one approved version per user (DB-enforced). Approving re-validates, supersedes the previous approved version and claims the draft in one transaction; races end in 409. Rejected/superseded versions are kept as history.
40. **Stale drafts**: a draft stores part hashes of preferences, appointments, unavailable periods and tasks. Approval is refused (409 `draft_stale`) if any part changed; every draft edit bumps `revision` (409 `stale_revision` on a mismatch).
41. **Approved plans are never silently rewritten.** After a change the approved view is flagged `needsRecalculation` (validator errors or unscheduled tasks, computed on read). The user generates a draft: `minimal` keeps still-valid future blocks, re-plans only displaced work, and keeps actual session history.
42. **Moves are validated by the backend with the same validator the engine uses**; a move is rejected if it introduces a new error (overlap, buffers, hours, dependencies, past). Previews do not write. Touch/keyboard users move via "Move to…" because drag-and-drop is mouse-only.
43. **ML**: one call per draft through the existing recommendation service with a session built from real free time and preferences. The ranking is only an order hint; constraints always win. If the call fails the schedule is produced from a rule-based order and the response says so. Formula and weights unchanged; no retraining.
44. **Postponement** sets `postponedUntil`, increments `postponeCount`, writes `TaskPostponement`, and never changes `dueDate`. Urgency is deadline-based, so postponing cannot make a task look less urgent than it is. Going past the deadline needs explicit confirmation.
45. **Actual vs planned**: actual work comes from finished focus timers; planned from approved blocks. Remaining time = estimate − finished timer minutes; this drives re-planning after an overrun.
46. **Time zones**: "now" and "today" use the user's IANA zone (default `Asia/Kolkata`). Scheduling itself works on wall-clock minutes with **no DST modelling**. Any valid IANA zone resolves "now" correctly; days containing a DST change are not handled specially. Tested zone: Asia/Kolkata (plus UTC and Asia/Tokyo for date resolution).
47. **Deferred (not implemented)**: recurring appointments/tasks and notifications/reminders. They need a reliable scheduler/worker and idempotent delivery; shipping them half-working was judged worse than deferring. Break resizing is also not supported (remove and re-add with the length you want).
48. **Test stand-in** (`test-support/memoryPrisma.js`) returns copies, serialises transactions and rolls back on error so atomicity and races are testable. It proves logic, not PostgreSQL behaviour; `test-db/` and the SQL constraint script cover that.
